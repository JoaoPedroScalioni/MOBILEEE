1. Abertura e Contextualização

O Projeto SafraCafé: O Problema e a Solução com Câmera e GPS

Breve relato de como o aplicativo substitui anotações manuais por captura ótica e auditoria geográfica direto no celular.

⚠️ O Problema no Campo
  • Ausência de Conectividade: As lavouras de café ficam em áreas rurais afastadas onde não há sinal de internet durante o dia.
  • Perda de Notas e Recibos: Comprovantes físicos de óleo diesel, manutenção e insumos rasgam, molham ou se perdem no campo.
  • Apontamento Lento e Manual: Anotar balaios em cadernetas de papel gera erros de digitação, rasuras e demora para identificar cada apanhador.
  • Falta de Rastreabilidade Geográfica: Sem coordenada GPS, não há como comprovar em qual talhão da fazenda a colheita ou despesa ocorreu.
💡 A Solução (Câmera + Geolocalização Local)
  • Câmera 1 — Leitura de Crachá QR Code: O apontador escaneia o crachá do trabalhador (TRAB-01, TRAB-2) e o app o seleciona em menos de 1 segundo.
  • Câmera 2 — Fotografia de Comprovantes: Ao lançar uma despesa, o app fotografa o recibo e salva o arquivo físico na memória permanente do celular.
  • Geolocalização Automática (GPS): Cada balaio colhido e cada despesa registrada capturam automaticamente a latitude e longitude do local.
  • Banco de Dados Local (SQLite): Todos os dados, coordenadas e endereços das fotos ficam gravados de forma relacional no próprio aparelho.
2. Princípios Arquiteturais: Clean Architecture e DDD

Onde Aparecem a Câmera e a Geolocalização?

Separação estrita de responsabilidades: o Domínio desconhece totalmente o hardware do celular e o banco de dados.

🏛️ Divisão em Camadas no Projeto
1. DOMAIN (src/domain/) — Núcleo Puro

Entidades (Trabalhador, Apontamento, Despesa), Value Objects (Coordinates, ValorMonetario) e Contratos. Zero código do Expo!

2. USE CASES (src/usecases/) — Casos de Uso

RegistrarApontamento e RegistrarDespesa. Recebem o repositório via Injeção de Dependência no construtor.

3. INFRASTRUCTURE & UI (src/infra/ & app/) — Adaptadores

É aqui que entram a Câmera e a Geolocalização! Módulos expo-camera, expo-image-picker, expo-location, LocalReceiptStorage e SQLite.

🧭 Por que a Câmera e o GPS ficam fora do Domínio?
Domínio Protegido: Para a entidade Despesa, não importa qual modelo de câmera tirou a foto, apenas que exista um endereço fotoUri válido e um objeto Coordinates íntegro.
Regra da Dependência: domain/ nunca importa de infra/ ou usecases/. As setas apontam sempre de fora (hardware/banco) para dentro (regras de negócio).
Ponto Único de Wiring: O arquivo src/infra/container.ts conecta os repositórios Singleton do SQLite aos casos de uso da aplicação.
3. A Estratégia de TDD

Como Testamos Câmera e Geolocalização?

Desenvolvimento orientado a testes validando regras geográficas e comprovantes fotográficos sem depender de sensores físicos.

🛠️ Como Foi Feito
  • Desacoplamento de Hardware: Em vez de acionar a lente física da câmera ou o chip GPS durante o teste, testamos os contratos e objetos que recebem esses sinais.
  • Repositórios In-Memory (Fakes): Criamos InMemoryDespesaRepository e InMemoryApontamentoRepository implementando as exatas interfaces do domínio.
  • Ciclo Red-Green-Refactor: Primeiro escrevemos os testes exigindo validação de coordenadas e URI de foto; depois implementamos as classes até todos os testes passarem.
  • Execução Ultrarrápida: As 36 suítes (134 testes) rodam em poucos segundos no Jest sem precisar abrir emulador Android.
✅ Nossos Testes Garantem Que:
  • Limites Geográficos Estritos: Nenhuma coordenada impossível (latitude fora de -90° a 90° ou longitude fora de -180° a 180°) entra no sistema.
  • Validação de URI da Câmera: Uma despesa com comprovante inválido (string vazia ou sem protocolo file://) é bloqueada imediatamente com erro de domínio.
  • Persistência Fiel dos Dados: Quando o caso de uso RegistrarDespesa ou RegistrarApontamento executa, o objeto salvo preserva exatamente a latitude, longitude e URI da foto recebidas.
  • Prevenção de Regressões: Qualquer alteração futura nas telas não quebra as regras de validação de colheita e despesas.
4. O Domínio e as Interfaces (A Base do Contrato)

Value Object Coordinates, Entidade Despesa e Contratos

A base do contrato: objetos imutáveis que se auto-validam no construtor e interfaces puras de repositório.

src/domain/value-objects/Coordinates.ts & Despesa.ts
// Value Object Imutável de Geolocalização export class Coordinates { constructor( public readonly latitude: number, public readonly longitude: number ) { if (latitude < -90 || latitude > 90) throw new Error('Latitude inválida: deve estar entre -90 e 90.'); if (longitude < -180 || longitude > 180) throw new Error('Longitude inválida: deve estar entre -180 e 180.'); } } // Contrato do Repositório (Interface Pura) export interface DespesaRepository { save(despesa: Despesa): Promise<void>; findAll(): Promise<Despesa[]>; }
📐 Engenharia do Domínio
Auto-Validação no Construtor (Fail-Fast): A entidade Despesa e o Value Object Coordinates validam seus dados no exato momento do new. Não existe objeto inválido em memória.
Validação da Foto na Entidade: Em Despesa.validate(), se fotoUri for informada sem formato de URI válido (ex: file:///...), a entidade lança Error('URI da foto inválida').
Contrato Desacoplado: A interface DespesaRepository exige apenas save(despesa). O domínio não sabe se será salvo em memória, no SQLite ou na nuvem.
5. O Teste (TDD na Prática) — Parte A: Geolocalização

Testando o Value Object Coordinates no Jest

Especificação executável que valida limites geográficos sem precisar de sinal de satélite real.

tests/domain/Coordinates.test.ts
describe('Coordinates Value Object', () => { it('deve instanciar coordenadas válidas', () => { const coord = new Coordinates(-21.2497, -45.5059); expect(coord.latitude).toBe(-21.2497); expect(coord.longitude).toBe(-45.5059); }); it('deve rejeitar latitude fora de [-90, 90]', () => { expect(() => new Coordinates(95, -45)) .toThrow('Latitude inválida'); }); it('deve rejeitar longitude fora de [-180, 180]', () => { expect(() => new Coordinates(-21, -185)) .toThrow('Longitude inválida'); }); });
🛰️ O que este teste explica e garante?
1. Caminho Feliz (Coordenadas Reais): Garante que coordenadas válidas da lavoura (ex: -21.2497, -45.5059) são armazenadas com precisão total e sem arredondamentos indevidos.
2. Proteção de Fronteira Terrestre: Se o sensor de GPS retornar lixo ou valores fora do globo (latitude > 90 ou longitude < -180), o construtor lança exceção na hora.
3. Barreira Antes do Banco Local: Nenhum apontamento ou despesa chega ao SQLite com localização corrompida, pois o domínio barra o erro em memória.
5. O Teste (TDD na Prática) — Parte B: Foto da Câmera & Use Case

Testando o Caso de Uso RegistrarDespesa com Fake em Memória

Validação completa do fluxo de registro de comprovante fotográfico e coordenadas usando repositório simulado.

tests/usecases/RegistrarDespesa.test.ts
it('deve registrar despesa com foto local e GPS', async () => { const repo = new InMemoryDespesaRepository(); const useCase = new RegistrarDespesa(repo); const output = await useCase.execute({ descricao: 'Combustível Trator', valor: 150.0, categoria: 'Transporte', latitude: -21.2497, longitude: -45.5059, fotoUri: 'file:///documentos/recibos/nota_1.jpg' }); expect(output.fotoUri).toContain('file:///'); expect(output.coordenadas.latitude).toBe(-21.2497); });
📸 O que este teste explica e garante?
1. Uso de Repositório Fake (Sem SQLite Real): Injetamos o InMemoryDespesaRepository no construtor do RegistrarDespesa, testando a regra de negócio pura em milissegundos.
2. Simulação da Câmera via URI Local: Passamos o endereço file:///documentos/recibos/nota_1.jpg simulando exatamente o retorno do armazenamento local do celular.
3. Garantia de Persistência Integrada: As asserções comprovam que a despesa salva mantém o vínculo entre o valor monetário, a foto do comprovante e a coordenada GPS.

7. Salvando os Dados no Celular — Parte A: Armazenamento Local da Foto

Como a Foto da Câmera É Salva Localmente no Aparelho?

A captura fotográfica gera uma URI persistente (Base64 / Sandbox local via LocalReceiptStorage) que é gravada no SQLite.

src/infra/filesystem/LocalReceiptStorage.ts & despesas.tsx
// 1. Captura da câmera com suporte a URI local e Base64 const result = await ImagePicker.launchCameraAsync({ mediaTypes: ['images'], allowsEditing: true, quality: 0.6, base64: true, }); // 2. Persistência no diretório interno do app (Sandbox) const receiptDir = `${FileSystem.documentDirectory}recibos/`; const permanentUri = `${receiptDir}recibo_${Date.now()}.jpg`; await FileSystem.copyAsync({ from: tempUri, to: permanentUri, });
📁 Funcionamento do Armazenamento Local
1. Captura Direta pelo ImagePicker: A câmera captura a imagem já comprimida (quality: 0.6) gerando a string de dados (data:image/jpeg;base64,... ou file://).
2. Diretório Seguro no Aparelho (LocalReceiptStorage): Arquivos file:// são copiados do cache temporário para a pasta definitiva documentDirectory/recibos/ do celular.
3. Renderização Imediata Sem Internet: O componente <Image source={{ uri: item.fotoUri }} /> lê a foto diretamente do banco local do aparelho, exibindo a miniatura na lista.
7. Salvando os Dados no Celular — Parte B: Persistência SQLite Relacional

Gravando Coordenadas GPS e Foto no Banco Local SQLite

Como o SqliteDespesaRepository e o SqliteApontamentoRepository persistem e reconstroem os objetos de domínio.

src/infra/sqlite/DatabaseClient.ts & SqliteDespesaRepository.ts
-- Tabela local no celular (safracafe.db) CREATE TABLE IF NOT EXISTS despesas ( id TEXT PRIMARY KEY, descricao TEXT NOT NULL, valor REAL NOT NULL, categoria TEXT, latitude REAL NOT NULL, -- Coordenada GPS longitude REAL NOT NULL, -- Coordenada GPS foto_uri TEXT, -- URI local da foto sync_status TEXT NOT NULL ); // Reconstruindo o Domínio ao ler do SQLite (mapRow) new Despesa( row.id, row.descricao, new ValorMonetario(row.valor), new Coordinates(row.latitude, row.longitude), new Date(row.data), row.foto_uri );
💾 Ciclo Completo no Banco Local
Desmontagem no save(): O repositório extrai despesa.coordenadas.latitude, despesa.coordenadas.longitude e despesa.fotoUri e executa o INSERT OR REPLACE no arquivo safracafe.db.
Remontagem no mapRow(): Na leitura (SELECT * FROM despesas), as colunas numéricas voltam a ser instâncias de new Coordinates(lat, lng) e new ValorMonetario(valor).
Persistência Definitiva no Aparelho: Mesmo que o aplicativo seja fechado, ao abrir novamente todos os balaios, fotos e coordenadas são carregados do SQLite local.
🚀 Próxima Etapa do Projeto (Evolução Planejada)

Próximo Marco: Sincronização em Nuvem com Supabase & Bucket S3

Como nossa arquitetura atual já deixa o terreno 100% preparado para enviar dados e fotos locais para a nuvem na próxima entrega.

🧱 O Que Já Deixamos Preparado Hoje
  • Coluna sync_status no SQLite: Todos os registros salvos hoje no celular já nascem marcados como pending (pendentes de envio).
  • Tabela sync_queue (Padrão Outbox): Cada gravação local já registra o evento em uma fila local, guardando a ordem exata das operações feitas offline.
  • Contratos Prontos no Domínio: Graças à Clean Architecture, o domínio não sofrerá nenhuma alteração quando conectarmos a nuvem.
☁️ Como Funcionará na Próxima Etapa
  • 1. Upload das Fotos para Bucket S3 (Supabase Storage): O app lerá o arquivo local (file:///.../recibos/foto.jpg) e subirá para um Bucket S3 na nuvem, recebendo uma URL pública HTTPS.
  • 2. Sincronização Relacional (PostgreSQL): Os trabalhadores, apontamentos (com latitude/longitude) e despesas serão enviados via upsert para o banco remoto do Supabase.
  • 3. Atualização Automática: Após o envio, o status local no SQLite mudará de pending para synced.
Vantagem Arquitetural: Como usamos Injeção de Dependência e Interfaces, conectar o Supabase na próxima etapa exige apenas adicionar os Gateways de nuvem na camada infra/, mantendo 100% do funcionamento offline atual.
