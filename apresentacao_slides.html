1. Abertura e Contextualização

O Problema e a Solução Tecnológica

Como o SafraCafé transforma a colheita agrícola unindo recursos nativos de hardware e software.

⚠️ O Problema em Campo
  • Ausência de Internet: As lavouras de café ficam em vales e morros sem 4G/Wi-Fi.
  • Perda de Comprovantes: Notas fiscais e recibos de insumos rasgam, molham e extraviam no campo.
  • Fraudes e Falhas de Apontamento: Erros manuais na pesagem e falta de comprovação de qual talhão foi colhido.
  • Lentidão no Registro: Anotação em caderneta manual gera retrabalho e erros na digitação posterior.
💡 A Solução SafraCafé
  • Câmera 1 (QR Code): Leitura ótica instantânea do crachá do trabalhador, eliminando digitação.
  • Câmera 2 (Evidência Fiscal): Foto do recibo na hora da compra de insumos, salva de forma permanente.
  • Geolocalização (GPS): Auditoria via latitude/longitude do talhão exato onde o café foi colhido.
  • 100% Offline-First: Gravação atômica no SQLite do celular e envio posterior para nuvem Supabase.
2. Princípios Arquiteturais

Clean Architecture & DDD: Onde Ficam a Câmera e o GPS?

A regra de ouro da arquitetura: O Domínio NUNCA depende dos recursos nativos do Expo.

🏛️ Camadas da Aplicação
1. DOMAIN (Núcleo Puro)

Entidades (Apontamento, Despesa) e VOs (Coordinates). Zero dependências externas.

2. USE CASES (Casos de Uso)

RegistrarApontamento, RegistrarDespesa. Recebem interfaces via Injeção de Dependência.

3. INFRASTRUCTURE & GATEWAYS (Adaptadores)

AQUI aparecem a Câmera e o GPS! expo-camera, expo-location, SQLite e Supabase.

🛡️ Por que essa separação é vital?
  • Independência de Framework: Se trocarmos a biblioteca da câmera no futuro, as regras de negócio de colheita não sofrem alteração.
  • Testabilidade Extrema: O domínio e os casos de uso são testados no Jest sem abrir simuladores pesados nem precisar de hardware real.
  • Inversão de Dependência (DIP): Use cases conhecem apenas interfaces abstratas; a infraestrutura implementa os contratos.
3. A Estratégia de TDD

Como Testamos Câmera e Geolocalização?

Como garantir a qualidade do software sem depender do satélite GPS nem do sensor físico da câmera.

🔬 Como foi feito (A Técnica)
  • Mocks e Fakes em Memória: Criamos FakeDespesaRepository e FakeApontamentoRepository para isolamento total.
  • Isolamento de Contratos: O caso de uso recebe o caminho da foto (string) e o par de coordenadas, sem acoplamento ao sensor nativo.
  • Execução Ultrarrápida: Todos os 130 testes rodam em memória em apenas ~6 segundos no Jest.
✅ Nossos Testes Garantem que:
  • Validação de Coordenadas: Latitudes fora de [-90, 90] ou longitudes fora de [-180, 180] são rejeitadas instantaneamente.
  • Integridade de Fotos: Uma despesa rejeita fotos com caminhos inválidos ou sem protocolo de arquivo.
  • Resiliência de Rede: O sistema grava no SQLite com status pending mesmo que a internet esteja desligada.
  • Zero Regressão: Nenhuma alteração futura quebrará a lógica de colheita existente.
4. O Domínio e as Interfaces

Value Object Coordinates: A Base do Contrato

A geolocalização como um Objeto de Valor imutável e auto-validado no construtor.

export class Coordinates { constructor( public readonly latitude: number, public readonly longitude: number ) { // 1. Auto-validação de latitude [-90 a +90] if (latitude < -90 || latitude > 90) { throw new Error('Latitude inválida'); } // 2. Auto-validação de longitude [-180 a +180] if (longitude < -180 || longitude > 180) { throw new Error('Longitude inválida'); } } }
💡 Explicação Resumida da Decisão
Imutabilidade: Propriedades readonly garantem que após criada, uma coordenada jamais seja alterada acidentalmente.
Auto-Validação: É impossível existir uma coordenada corrompida na memória da aplicação; o construtor rejeita valores absurdos.
Isolamento DDD: Este arquivo não importa nenhuma biblioteca externa (nem Expo, nem React Native). Domínio puro.
5. O Teste (TDD na Prática)

Asserções Automatizadas no Jest

Como as especificações foram escritas antes mesmo da implementação da interface gráfica.

// tests/domain/Coordinates.test.ts describe('Coordinates Value Object', () => { it('deve instanciar coordenadas válidas', () => { const coord = new Coordinates(-21.2488, -44.9998); expect(coord.latitude).toBe(-21.2488); expect(coord.longitude).toBe(-44.9998); }); it('deve lançar erro se latitude > 90', () => { expect(() => new Coordinates(91, 0)) .toThrow('Latitude inválida'); }); it('deve lançar erro se longitude < -180', () => { expect(() => new Coordinates(0, -181)) .toThrow('Longitude inválida'); }); });
🎯 O que este teste garante?
Caminho Feliz: Coordenadas reais de lavouras cafeeiras são aceitas com precisão decimal máxima.
Limites de Fronteira: Valores absurdos retornados por falhas de GPS ou entradas corrompidas quebram no teste.
Confiança Cega: Quando a tela do celular usa o VO Coordinates, temos a certeza matemática de que o dado é válido.

7. Salvando no Banco de Dados Local

Persistência SQLite Relacional & Local FileSystem

Como as coordenadas de GPS e as fotos da câmera são salvas com segurança no aparelho.

-- DDL da Tabela de Despesas no SQLite CREATE TABLE IF NOT EXISTS despesas ( id TEXT PRIMARY KEY, descricao TEXT NOT NULL, valor REAL NOT NULL, latitude REAL NOT NULL, -- GPS longitude REAL NOT NULL, -- GPS foto_uri TEXT, -- FileSystem sync_status TEXT NOT NULL ); -- DDL da Tabela de Apontamentos (Colheita) CREATE TABLE IF NOT EXISTS apontamentos ( id TEXT PRIMARY KEY, trabalhador_id TEXT NOT NULL, litros REAL NOT NULL, latitude REAL NOT NULL, longitude REAL NOT NULL, sync_status TEXT NOT NULL );
🔒 Decisões de Engenharia Críticas
Por que NÃO salvar imagem em Base64 no SQLite? Base64 causaria alto consumo de memória RAM e estouro de buffer (OOM). Salvamos o arquivo binário no FileSystem e gravamos apenas o caminho (URI) no banco relacional.
Reconstrução Limpa no Repositório: O SQLite armazena floats primitivos. Ao ler com mapRow(), o repositório remonta o Value Object puro new Coordinates(row.latitude, row.longitude).

8. Replicação Online & Nuvem

Sincronização Online com Supabase & Storage S3

Como as fotos e os dados tabulares do SQLite sobem para a nuvem de forma resiliente.

☁️ Fluxo em Duas Etapas
1. Upload de Mídia (Bucket S3 'recibos'): O gateway envia a imagem binária do recibo para o Supabase Storage e obtém uma URL pública HTTPS permanente.
2. Upsert Idempotente no PostgreSQL: O gateway insere ou atualiza o registro no banco remoto com resolução de conflitos Last-Write-Wins via updated_at.
3. Limpeza da Fila: Após confirmação da nuvem, o item no SQLite é marcado como synchronized.
// Trecho do SupabaseSyncGateway.ts if (tabela === 'despesas' && record.foto_uri?.startsWith('file://')) { // 1. Sobe foto para o Bucket S3 const upload = await this.storageGateway .uploadFile(record.foto_uri, path); record.foto_uri = upload.publicUrl; } // 2. Upsert na tabela relacional await supabase .from(tabela) .upsert(record, { onConflict: 'id' });
