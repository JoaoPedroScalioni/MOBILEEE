1. Abertura e Contextualização

O Problema no Campo e a Solução Tecnológica

Como o SafraCafé transforma a gestão da colheita de café unindo sensores nativos, persistência local e nuvem.

⚠️ O Problema em Campo
  • Oscilação de Internet: As lavouras de café ficam em vales e regiões rurais com sinal 4G instável ou inexistente.
  • Perda de Comprovantes: Notas fiscais e recibos de óleo, transporte e insumos rasgam, mancham ou extraviam no campo.
  • Erros de Apontamento: Anotações manuais dificultam comprovar a litragem colhida e a localização exata do talhão.
  • Retrabalho Operacional: Digitar cadernetas no fim do dia atrasa o fechamento de diárias e colheitas.
💡 A Solução SafraCafé
  • Câmera 1 (QR Code): Leitura ótica instantânea do crachá do colhedor (ex: TRAB-01, TRAB-2), sem digitação.
  • Câmera 2 (Comprovante Fiscal): Fotografia do recibo na hora da despesa, enviada automaticamente para o Bucket S3.
  • Geolocalização (GPS): Auditoria via latitude/longitude exata vinculada a cada apontamento e despesa.
  • Offline-First + AutoSync: Gravação atômica no SQLite local com sincronização automática em background para o Supabase.
2. Princípios Arquiteturais

Clean Architecture & DDD: Onde Ficam a Câmera e o GPS?

A regra central da arquitetura: o Domínio nunca importa bibliotecas nativas do Expo ou do banco de dados.

🏛️ Camadas da Aplicação
1. DOMAIN (Núcleo Puro)

Entidades (Trabalhador, Apontamento, Despesa) e Value Objects (Coordinates, CPF, Volume). Zero dependências externas.

2. USE CASES (Casos de Uso)

RegistrarApontamento, RegistrarDespesa, SincronizarDados. Recebem contratos via Injeção de Dependência.

3. INFRASTRUCTURE & GATEWAYS (Adaptadores)

Aqui vivem a Câmera, o GPS e o Banco! expo-camera, expo-image-picker, expo-location, SQLite e Supabase.

🛡️ Benefícios Práticos dessa Separação
  • Independência de Hardware: Se trocarmos a biblioteca de câmera ou de GPS, nenhuma regra de negócio do domínio precisa ser alterada.
  • Testabilidade em Milissegundos: O domínio e os casos de uso são validados no Jest sem precisar de emulador Android nem satélite real.
  • Inversão de Dependência (DIP): O arquivo container.ts conecta os repositórios Singleton SQLite e Gateways Supabase aos casos de uso.
3. A Estratégia de TDD

Como Testamos Câmera, GPS e Sincronização?

Garantia de qualidade automatizada sem depender do sensor físico da câmera nem do sinal de satélite.

🔬 Técnica de Isolamento
  • Repositórios Fake em Memória: Implementamos FakeDespesaRepository e FakeApontamentoRepository seguindo os mesmos contratos do SQLite.
  • Desacoplamento de Sensores: Os casos de uso recebem o payload validado (URI/data-URI da foto e par de coordenadas), isolando o hardware.
  • Execução Rápida: As 36 suítes com 134 testes unitários executam em menos de 6 segundos no Jest.
✅ O que os Testes Garantem
  • Fronteiras Geográficas: Latitudes fora de [-90, 90] ou longitudes fora de [-180, 180] lançam exceção imediata.
  • Integridade de Comprovantes: A entidade Despesa valida protocolos de mídia (file://, https:// e data:image/jpeg;base64).
  • Fila Outbox Confiável: Toda gravação local entra como pending e transita para synced após confirmação do servidor.
  • Resolução de Conflitos: O serviço de sincronização aplica Last-Write-Wins baseado no timestamp updatedAt.
4. O Domínio e as Interfaces

Value Object Coordinates & Entidade Despesa

Objetos imutáveis e auto-validados no construtor protegem a integridade dos dados antes de chegar ao banco.

// src/domain/value-objects/Coordinates.ts export class Coordinates { constructor( public readonly latitude: number, public readonly longitude: number ) { if (latitude < -90 || latitude > 90) throw new Error('Latitude inválida'); if (longitude < -180 || longitude > 180) throw new Error('Longitude inválida'); } } // src/domain/entities/Despesa.ts (Validação de Foto) const isValidUri = this._fotoUri.includes('://') || this._fotoUri.startsWith('data:'); if (!isValidUri) throw new Error('URI da foto inválida');
💡 Decisões de Modelagem
Imutabilidade: Propriedades readonly impedem mutações acidentais nas coordenadas capturadas pelo GPS.
Auto-Validação (Fail-Fast): Qualquer coordenada ou URI inválida é barrada na criação da entidade, mantendo o banco limpo.
Suporte Híbrido de Mídia: Aceita tanto URI local/remota (file://, https://) quanto payload em memória (data:image/jpeg;base64).
5. O Teste (TDD na Prática)

Asserções Automatizadas no Jest

Especificações executáveis garantem o comportamento de coordenadas, entidades e casos de uso.

// tests/domain/Coordinates.test.ts describe('Coordinates Value Object', () => { it('deve instanciar coordenadas válidas', () => { const coord = new Coordinates(-21.2497835, -45.5059581); expect(coord.latitude).toBe(-21.2497835); expect(coord.longitude).toBe(-45.5059581); }); it('deve lançar erro se latitude > 90', () => { expect(() => new Coordinates(91, 0)) .toThrow('Latitude inválida'); }); it('deve lançar erro se longitude < -180', () => { expect(() => new Coordinates(0, -181)) .toThrow('Longitude inválida'); }); });
🎯 O que este teste garante?
Precisão Real de Campo: Coordenadas reais capturadas no celular (ex: -21.2497835, -45.5059581) são preservadas com total fidelidade.
Limites de Fronteira: Valores inválidos gerados por leituras corrompidas são imediatamente bloqueados.
Segurança na Persistência: Quando o repositório SQLite ou o Supabase recebe o dado, o domínio já atestou sua validade.

7. Salvando no Banco de Dados Local

Persistência SQLite Relacional & Fila Outbox

Estrutura de tabelas relacionais no dispositivo móvel (safracafe.db) para operação 100% offline-first.

-- Tabelas principais no SQLite (DatabaseClient.ts) CREATE TABLE IF NOT EXISTS despesas ( id TEXT PRIMARY KEY, descricao TEXT NOT NULL, valor REAL NOT NULL, categoria TEXT, latitude REAL NOT NULL, -- GPS (-21.2497801) longitude REAL NOT NULL, -- GPS (-45.5059631) foto_uri TEXT, -- URI local ou URL pública S3 sync_status TEXT NOT NULL ); CREATE TABLE IF NOT EXISTS sync_queue ( id TEXT PRIMARY KEY, operacao TEXT NOT NULL, tabela TEXT NOT NULL, registro_id TEXT NOT NULL, payload TEXT NOT NULL, tentativas INTEGER DEFAULT 0 );
🔒 Engenharia de Persistência Local
Padrão Singleton no Banco: DatabaseClient.getInstance() garante uma única conexão SQLite ativa com suporte a PRAGMA foreign_keys = ON.
Reconstrução de Domínio: Ao ler os números decimais do SQLite, o método mapRow() reconstrói o Value Object new Coordinates(row.latitude, row.longitude).
Atualização Pós-Upload: Assim que a foto sobe para o S3, o SQLite substitui o payload local pela URL HTTPS pública do bucket e marca sync_status = 'synced'.

8. Replicação Online & Nuvem

AutoSync, Decodificação Binária & Supabase S3

Como o SupabaseSyncGateway e o SupabaseStorageGateway transmitem fotos e registros sem corrupção.

☁️ Pipeline de Sincronização
1. Decodificação Base64 → Uint8Array: Converte a foto capturada em bytes binários puros (image/jpeg) e envia ao bucket recibos/comprovantes/.
2. Upsert Idempotente no PostgreSQL: Grava o registro nas tabelas trabalhadores, apontamentos e despesas com a URL pública do S3.
3. Confirmação e Limpeza da Fila: Retorna serverUpdatedAt: item.updatedAt, removendo o item da sync_queue e zerando as pendências.
// SupabaseSyncGateway.ts — Upload S3 + Upsert SQL if (item.tabela === 'despesas' && !record.foto_uri.startsWith('http')) { const up = await this.storageGateway .uploadFile(record.foto_uri, storagePath); record.foto_uri = up.publicUrl; } await this.supabase .from(item.tabela) .upsert(record, { onConflict: 'id' }); // Marca 'synced' no SQLite e limpa fila Outbox return { serverUpdatedAt: item.updatedAt };
